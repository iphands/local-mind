jev: decision-model hints for OpenCode

jev hands small classification jobs to H2O Lightning 4B, a 4B decision model running on the RTX 4060. It never asks the model to write text. It sends a block of text (the state) and multiple-choice questions, and the model returns a probability for each option. One answer costs one prefill and no decoding: about 125 ms for a shell command. Three hooks add hints and tighten permissions. One tool, ask_jev, lets an agent ask a question about files without reading them.

Only addsHint text on prompts and tool results. Command output is never edited.
Only tightensA permission can go from allow to ask, never the other way, and never to deny.
Never blocksNo hook throws. Both reviewers always run.
Fails openIf the server is down, slow or wrong, the hooks behave as if jev weren't installed, and ask_jev says to read the files instead.

Usage

jev loads automatically from ~/.config/opencode/plugins/ and needs no setup. These are the controls.

Trace view on / off

Shows each request and raw response as JSON in the TUI. Off by default. Takes effect on the next call, with no restart.

# inside the ocli container
touch ~/.config/opencode/jev-trace   # on
rm    ~/.config/opencode/jev-trace   # off

# from the host
touch opencode/container_data/config/opencode/jev-trace

Environment (read at startup)

JEV_URL=http://cosmo.lan:8701   # decision server
JEV_DISABLE=1                   # register no hooks and no tool
JEV_TRACE=1                     # trace view always on

Set these in the opencode serve environment. Changes need a serve restart.

Ask about files (ask_jev)

Agents call it themselves; you can also ask for it: "without reading them, use ask_jev to find which files under src/ talk to the database".

{ "paths": ["src/**/*.rs"],
  "question": "Does this file use a mutex or read-write lock?" }

Long command output

When OpenCode cuts a result short with full output saved to <path>, pass that path to ask_jev: "did any test fail?" over a 20k-line log, without reading it.

F1

Reviewer pre-screen

execute.before on subagent · 15 s timeout

When the agent launches neckbeard or hoodie, jev asks three questions about the change in one request. Then it appends a short block to the end of the reviewer's prompt. Each reviewer sees only its own flags.

Fires on
a new reviewer launch. A follow-up to a running review (input has a sessionID) is left alone
State
the fenced code blocks and diffs in the prompt, or the whole prompt if there are none. Over 24k characters (~6k tokens), the start and end are kept
Questions
  • neckbeard_flag: type_suppression, empty_catch, weakened_test, hardcoded_secret, injection, null_unhandled, logic_bug
  • hoodie_flag: quadratic, io_in_loop, unbounded_load, missing_cache, blocking_sync, poor_error_message
  • risk: trivial / standard / risky
Thresholds
flags listed at p ≥ 0.15 · "quick consultation" when trivial ≥ 0.80 and neither reviewer has a flag · "do a full review" when risky ≥ 0.60
Sharing
both reviewers launch in one message and share one request. The in-flight promise is cached, keyed by a hash of the state
## Decision-model pre-screen (a 4B model's hints, not findings — confirm or refute each flag first)
- flags: empty_catch p=0.41, logic_bug p=0.18
- risk: standard p=0.72
neckbeard.md and hoodie.md tell the reviewers to confirm or refute each flag, to treat an empty block as proving nothing, and to ignore "quick consultation" if they find a serious issue.
F2

Shell verdict

execute.after on shell · 8 s timeout

Catches commands that exit 0 but didn't really work: test runners behind || true, scripts that print errors and still exit 0, builds that pass with warnings worth reading. It adds one line to the tool result.

Runs when
all of these hold: exit 0 · output ≥ 200 characters · the command doesn't start with a read-only tool (cat, ls, grep, rg, find, sed -n, jq, diff, git status|log|diff|show|…)
State
the command, the exit code and the last ~16k characters of output
Question
pass / fail / warnings / inconclusive
Thresholds
below 0.50 the line says unsure (leans …). A failure hidden behind exit 0 scored 0.55 in calibration · the runner-up is shown at ≥ 0.20
Read-only check
looks only at the start of the command, so cd dir && git status still gets a verdict
[jev] verdict: pass p=0.90 (decision-model hint, not a review; exit=0)
[jev] verdict: fail p=0.71, pass p=0.24 (decision-model hint, not a review; exit=0)
[jev] verdict: unsure (leans fail) p=0.44 (decision-model hint, not a review; exit=0)
local-mind.md tells the main agent the verdict is a hint, never verification. Command output still goes to both reviewers, verdict line included.
F3

Shell risk escalation

permission evaluate · 8 s timeout

For a shell command the config would run without asking, jev asks two questions in one request. If either one is confident the command is dangerous, the permission becomes ask and you confirm it in the TUI.

Runs on
shell commands with effect allow only. ask and deny rules in opencode.jsonc are never touched
shell_risk
routine / destructive / network / system. Any non-routine label ≥ 0.70 escalates
reversibility
read_only / reversible / irreversible, with worked examples in each criterion. If shell_risk found nothing, irreversible ≥ 0.85 escalates. It only adds escalations: it never cancels a shell_risk hit
Message
reports the shell_risk label when both fire. Otherwise it says irreversible
rm fast path
an rm whose every target is a plain relative path inside the working directory (no / ~ $ .., bare ., globs, pipes, redirects, ; & or $(…)) stays allow with no model call. The model scores any rm as destructive (rm -rf target/ 0.94 vs rm -rf ~/x 0.96)
jev flagged this command as destructive (p=0.93); confirm to run it
jev flagged this command as irreversible (p=0.96); confirm to run it

F4

ask_jev: questions about files, without reading them

ctx.tool.transform · runs under the read permission

An agent asks one question about many files. Each file is judged separately, and the agent gets one line per file: the answer, its probability, and the line range that decided it. None of the file text enters the agent's context. It is a scouting tool: find what's worth reading, then read only that.

ask_jev: "Does this file use a mutex or read-write lock?" (yes/no) · 17 files · 398k chars · 113,819 tokens judged in 28.8 s
yes 0.95  llama-proxy/src/augment.rs  (lines 1079-1249)
yes 0.91  llama-proxy/src/backends/mod.rs  (lines 1-197)
…
unsure (leans no) 0.69  llama-proxy/src/backends/balancer.rs
not checked (budget; ask again with these paths): llama-proxy/src/exporters/influxdb.rs, … (+13)
jev answers are a 4B classifier's guesses: read a file before editing it, quoting it, or relying on the answer.
Arguments
  • paths: 1–20 files, directories or globs (src/**/*.ts), relative to the project, or a saved tool-output path
  • question: one question, answered per file
  • options (optional): {label: description}, 2–8 labels, with the question phrased as a choice ("Which of these…?"). Without it, the question is yes/no
Who sees it
every agent allowed to read: local-mind, chat, neckbeard, hoodie
Permissions
each file gets the same read check as the read tool, so the reviewers' *.env denies apply. A denied file is listed and the call goes on
Paths
inside the directory or project, plus ~/.local/share/opencode/tool-output/. Globs and directories expand with rg --files (.gitignore respected, hidden files skipped). At most 50 files. Binary files are skipped
Judging
files are split into ~8000-character chunks with 20 lines of overlap, one request each. Yes/no: a yes in any chunk counts, and its line range is shown. Options: length-weighted average, and a part that leans elsewhere is noted. Below 0.70 a line reads unsure (leans …)
Queue
requests go one at a time across all ask_jev calls, so parallel calls wait for each other: more in flight adds no throughput (flat from 1 to 8 clients) and would take slots from the hooks, which never wait here. An interrupted call that is still queued ends at once
Budget
at most 400k characters per call (~29 s). Files past that are listed as not checked. A file over 200k characters is checked from the top and marked partial. One glob can cover the whole call, so there's no reason to batch
Failure
15 s per request. The first failure stops the call with what it has. With nothing answered, the tool errors: jev is unavailable (…); read the files instead

Trace view

For debugging. While it's on, each request jev sends (a preview of the state plus the questions in full) and the raw response go into the TUI as formatted JSON.

Where each trace appears

  • F1 on the reviewer's result, matched by tool call id. Never on its prompt, so reviewers get the same input either way
  • F2 on the shell result, after the verdict line
  • F3 on the same shell call's result, matched by command text (the permission event has no call id)
  • F4 on the ask_jev result: one summary block with the first request, request count, tokens and per-request time

A trace waiting for its result is dropped after 10 minutes, or once 16 others are queued (for example when you reject a command at the ask prompt).

Reading a trace

  • request.state: cut to 800 characters (start and end)
  • response: the server's body, exactly as received
  • error instead of response: the fetch error, HTTP 404: …, malformed answer for …, or skipped: cooling down after a failure (42s left)
  • ms: request time

A trace is part of the tool result, so the main agent reads it too. An F1 trace is about 3k characters.

[jev trace] F2 shell verdict

  "request": {

Fail-open: safe when the server is down

If the decision server is down, slow or returns nonsense, OpenCode behaves as if the plugin weren't there. Seven mechanisms guarantee that.

Every failure is "no answer"

query() never throws. Connection refused, DNS failure, timeout, a non-2xx status (including a stock GGUF with no /v1/systemone), bad JSON or a missing answer all come back as answers: null, and the hook leaves the call alone.

One failure pauses every feature for 60 s

A dead server costs at most one timeout a minute. With connection refused, the pause costs nothing noticeable. Calls during the pause skip the network entirely. ask_jev respects the pause but only starts one when the server can't be reached at all: its timeouts never switch off F3.

Hooks never throw

Every hook body runs inside guard(), which logs [jev] <hook> hook error, passing through and returns. This matters most for F1: a throw from execute.before would block the reviewer launch.

Changes happen last, all at once

Each hook builds its change and assigns it in one step at the end (e.input, e.result, e.effect). A failure before that leaves the event untouched.

No answer means no change

F1: the prompt is sent unchanged and both reviewers run. F2: no [jev] line. F3: allow stays allow. F4: the tool errors with "read the files instead", or returns what it has plus stopped early.

Failures are not cached

The F1 cache drops failed results, so the next launch after the pause tries again.

Startup doesn't depend on the server

setup() only registers hooks and logs the URL. It never contacts the server.

What you lose while it's down: F3's extra prompts. Shell permissions fall back to the rules in opencode.jsonc. The worst cost of an unreachable host is one 8 s or 15 s wait, then the 60 s pause.

The decision server

Launcherserver/llamacpp/run-jev-4060, on the RTX 4060 (device=1)
EndpointPOST http://cosmo.lan:8701/v1/systemone (llama.cpp build ≥ 11773; probed against b12169)
Slots8, sharing one 40960-token KV pool (--parallel 8 --kv-unified), chosen by server/llamacpp/run-jev-4060-benchmark · peak 7.06 GiB

// request
{ "state": "<text to judge, question included>",
  "questions": { "verdict": { "type": "choice",
                              "criteria": { "pass": "the command succeeded ...", "fail": "the command failed ..." } } } }
// response
{ "answers": { "verdict": { "choice": "pass", "probabilities": { "pass": 0.90, "fail": 0.04 } } } }

The question lives in state

Unknown keys such as question are ignored by the server.

Criteria carry the meaning

The model reads each option's description, so the wording matters more than the label. Each question re-prefills the whole state, so checklists go into one question.

Checking it

Probe the server by hand

curl -s http://cosmo.lan:8701/v1/systemone \
  -H 'content-type: application/json' -d '{
  "state": "A coding agent ran a shell command.\n\n$ make test\nexit code: 0\n\n3 passed, 1 FAILED",
  "questions": {"verdict": {"type": "choice", "criteria": {
    "pass": "the command succeeded and its output shows no errors or failures",
    "fail": "the command failed: errors, failing tests, crashes or panics"}}}}'

Confirm it fails open

Stop the 4060 container and run a shell command that prints more than 200 characters. No [jev] line comes back, and the log shows one unavailable … skipping for 60s. With the trace view on, the same call shows a trace with an error.

jev.ts exports __test (the client, state builders, question sets and thresholds) for scripts. The plugin loader reads only default.
