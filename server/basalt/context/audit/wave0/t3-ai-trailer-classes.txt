# T3 · AI co-authorship trailer **classes** — the published census under-counts by four tool families

Asked by: the T2 sign-off review, which noted that PR #47 carries `Co-Authored-By: opencode` and
that `t2-provenance.txt` § 10 tallies only Claude, human and Codex. A fourth class is now known to
exist, so the published figures had to be re-derived rather than trusted. Nothing here was typed:
every number below is emitted by the computation this file was generated from.

## 1 · The published figures reproduce **exactly** under their own pattern

The owner of these numbers is `t2-provenance.txt` § 10 (*What the corpus's own metadata says wrote*

```text

```

```text

```

So the arithmetic in § 10 was right. The defect is in the **net**, not the count — which matters,
because it means § 10's careful caveats were all sound and only its denominator was narrow.

## 2 · A wider net is a **strict superset**: nothing is lost, 26 commits are gained

```text
A  published pattern                           1881
B  any Co-Authored-By naming a tool family     1907
A|B corrected                                  1907 of 2194 = 86.9%   (published 85.7%)
A\\B  published catches, wider net misses          0   <- 0 means B is a strict superset of A
B\\A  wider net catches, published misses         26
```

`A\\B = 0` is the load-bearing line: the correction cannot be dismissed as a different measurement
that trades one set of omissions for another. Every commit § 10 counted is still counted.

## 3 · The mechanism: the alternation is anchored to the token **after the colon**

```text
True   Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
False  Co-Authored-By: Codex <noreply@openai.com>
True   Co-Authored-By: OpenAI Codex <codex@openai.com>
False  Co-Authored-By: codex <noreply@openai.com>
```

`Codex <noreply@openai.com>` is an OpenAI-family trailer that § 10's own family **fails to catch**,
because the token immediately after the colon is `Codex`, not `openai`. Anchoring on the **domain**
instead catches all four lines. So § 10 under-counts even the two families it set out to count.

### 8b · Making the ancestor measurement checkable without trusting this scratch store

The clone in `/tmp` is scratch: it is not evidence and it can rot. So the measurement is stated with
its full inputs, and a reader who re-fetches can confirm they landed on the same corpus before
believing the `8`.

```bash
# exact fetch (public, unauthenticated, ~4 MiB)
git init strata-pristine && cd strata-pristine
git remote add origin https://github.com/Niko1221/Strata
git fetch --filter=tree:0 origin main:refs/remotes/origin/main

# the producer of this section
git log -z --format='%H%x00%B' refs/remotes/origin/main > bodies.bin
# then the identical A / B computation from sections 1-2 above (A = § 10's pattern, B = domain-anchored)
```

Composition of the store this was measured against, so a re-fetch can be verified as equivalent:

```text
ref           refs/remotes/origin/main
tip           ffa80d73133ea5c548aefe57889a16e8085a938f   2026-11-02T23:37:27+01:00   Niko1221
commits       5637                     <- reproduces § 10's published denominator exactly
objects       6347 commit / 3131 tree / 0 blob           (partial clone: filter=tree:0, promisor=true)
in-pack       13180 across 4 packs, 3.80 MiB
```

Two properties of that composition matter for reproducibility. The clone is **partial** (`tree:0`,
promisor): blobs are fetched on demand, so `git log` over commit objects works offline but reading a
*blob* would touch the network — which this measurement never does, it reads commit messages only.
And **commit 6,347 against 5,637 reachable** is not a contradiction: the store holds objects from
more than one fetch, and the count that matters is the reachable `rev-list --count`, which is 5,637.
Given the tip and the reachable count matching, a reader who re-fetches and gets `A = 3` has the same
corpus § 10 measured, and `B = 8` is then a one-line recomputation.

## 9 · Derived comparisons: what the repair moves, and what it does not

Correcting two rates is not the same as correcting every claim computed *from* them: a ratio of two
rates moves non-linearly, so sweeping the figures alone cannot find it. Each derived claim was
re-derived instead.

```text
whole-corpus asymmetry   published   85.734 % / 0.0532 % = 1,611x   (log10 3.21)
                         corrected   86.919 % / 0.1419 % =   612x   (log10 2.79)   -> 2.63x narrower
```

**No text anywhere in `context/` states that ratio**, searched for `[N]×`, `× N`, `times`,
`orders of magnitude`, `factor of`, `asymmetry`, `stark`, `disproportionate` across every prose file
(the `×` hits are KV-slot arithmetic and file-mode histograms). So nothing to correct — and the ratio
is recorded here rather than added elsewhere, because 612× is a *derived* figure that should be
re-computed from the two rates at their owner rather than restated. "**Two orders of magnitude**"
survives: 3.21 → 2.79 rounds to the same order of magnitude on both sides of the repair.

The pair-level table that the lineage finding actually rests on (`t2-lineage.txt` § 5) was re-derived
from scratch — **the two repositories joined across two separate object stores** by the
`(tree, author-date, committer-date, subject)` key, which is an independent replication of a table
T2 produced from one combined store:


narrow pattern in the first place. `1,049 vs 0` reproduces exactly, and the asymmetry that
`t2-lineage.txt` § 5 uses to rule out a cosmetic rebase survives the repair untouched.
