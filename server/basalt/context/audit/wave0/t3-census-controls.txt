## Why this file exists

RULES.md: a tool's clean output is worthless until it has been shown to report something. `34/34 PASS`
on the real tree says nothing on its own — one of those 34 was *already known* to be a tautology
(`SORT_DEFAULT_ORDER_EQ_C`'s first cut compared `sort` output to `"Bab"` inside a process that had
exported `LC_ALL=C` twelve lines earlier) and three more were strict logical implications of their
neighbours. Knowing the count and checking the count are different acts; the same goes for knowing an
assertion *could* fail.

How the truncated hashes above got past a check that appeared to catch them is
`pitfalls.md` § *A commit is the index, not the file I was looking at*.

## Method — four rules, each learned by getting it wrong

1. **The repo script is never mutated.** A copy is made **beside the original**
   (`context/audit/scripts/.neg-<name>.sh`), run from the project root, and deleted after. Reason: the
   script resolves `MAN`/`PROJ` from its own location (`$SELF`); a copy parked in `/tmp` resolves the
   manifest to `/tmp/manifest` and dies at `MANIFEST_DIR_NOT_FOUND` (exit 2) **before any assertion
   runs** — which reads like a control that failed to fire rather than a control that never ran.
2. **The mutation is an exact-string replacement that must match exactly once**, else the harness
   refuses with `VACUOUS n=<count>` and runs nothing. A `sed` that silently matches nothing produces a
   clean run of an *unmodified* script — the worst possible control, because it reports green about
   green. Byte-difference from the original is therefore guaranteed before execution.
3. **A control passes only if: exit 1, `T3_CENSUS_VERDICT=FAIL`, and the named assertion's own line
   reads FAIL.** A run that dies at exit 2 is a broken control, not a fired one.
4. **What the per-block `GENERATOR_SHA=` tokens are actually backed by — a withdrawal, 2026-11-05.** A
   draft of this header claimed every token was re-derivable as `sha256(frozen base + the printed
   one-substitution)`, which would have made the scratch transcripts unnecessary. **That claim is false,
   and it was tested the same day it was written.** Measured: each `mutate:` pair's left-hand side occurs
   **exactly once** in the frozen script (10 of 10 — the recipes locate correctly, so this is not a
   transcription failure of that kind), but re-deriving from the frozen base reproduces **0 of the 9**
   re-derivable tokens (C1's is `deadbeef` by construction and is excluded). The base was **not** the
   frozen script. The clean case is C2: its mutation is a one-token change on a standalone line
   (`SENT_TOTAL_FLOOR_REAL=34`, unique in the file), so if its base had been `1bab1ec5…` its token would
   follow arithmetically — it does not. And `context/audit/scripts/t3-census.sh` carries **mtime
   2026-11-05 06:35:10**, i.e. after the last control in this file ran (06:35:08) and four seconds before
   the `real` run this plan pastes (06:35:14): **the generator was rewritten after this batch was
   collected.** The bytes these ten mutants were cut from are unrecoverable — exactly one blob of that
   file has ever been committed (`1bab1ec5…`), and the mutant copies that rule 1 requires are deleted
   after each run, per rule 1.

   Consequence, stated where the tokens are used: **they are witnessed, not re-derivable.** What carries
   them is the transcripts' `ARGV=` (which names the mutant, `.neg-<name>.sh`) and `GENERATOR_SHA256=`
   line, and `/tmp/opencode/neg-*.txt` is scratch that will not exist for a later reader. What *does*
   survive in this file is the recipe, the assertion that fired, and its verdict — and **that half was put
   to the test rather than asserted.** **[MEASURED 2026-11-05]** Re-applying each `mutate:` pair to the
   frozen `1bab1ec5…` script and running it under `tag=negctl` fires the named assertion in **9 of the 9**
   controls that can be tested on that tag: exit 1, `T3_CENSUS_VERDICT=FAIL`, and the target assertion's own
   line reading FAIL (`GENERATOR_SHA_SAME_AS_REAL` fails alongside every one of them, which is correct — a
   mutant is not the baseline generator — and is itself proof that `run-real` was still holding the pristine
   token throughout). **C2 is the stated limit**: its target,
   `SENTINEL_TOTAL_AT_OR_ABOVE_FLOOR`, is one of the 11 real-only assertions, so it cannot be re-fired
   without running a mutant under `tag=real` — which is § 4's defect, and § 4 is why the answer is no. So
   the sentence "re-make the mutation and watch the same assertion fail" is now backed by a run rather than
   being a prediction about a program that no longer exists, which is what it was when neckbeard flagged it.
   Not enough to reproduce a hash, though: that half stays withdrawn. Two corroborations worth keeping: the
   tokens are **program** identities, not run identities — `label_gone` and `retry` are different
   transcripts carrying the **same** `GENERATOR_SHA256` (see the count disclosure above); and C9's recipe
   lost its argument to the terminal ellipsis, so the pair above had to be **completed by inference** — that
   inference reproduces the original transcript's output line **byte-for-byte**, which is the only machine
   comparison of a hand-typed value in this file, and the reason § 4 says "matches, as typed" where this
   one can say "identical".

## 2 · What is NOT controlled

Stated because an unlisted gap is a gap someone fills by guessing.

- **No canary control exists.** Six planted primitives, one per class, do not exist yet. Until
  `t3-canary-score.tsv` has 6 rows the census cannot print plain `PASS`. By design, not oversight.
- **The universe is a PATH SET, so the harness cannot see a content modification at all.** **[OBSERVED
  2026-11-05, found while pre-flighting the canary fixture]** `universe.txt` is one path per line —
  `UNIVERSE_SHA256` is flagged as such at `t3-census.sh:225` ("a hash of the sorted path set, NOT git's tree
  hash: the tree hash covers contents and this one does not"), and the tree-diff at `:260-261` is `comm`
  over those two path lists, so a file whose **path** is unchanged but whose **bytes** differ appears in
  neither `tree-added.txt` nor `tree-removed.txt`. Consequences, all three of them load-bearing for the
  canary design: **(1)** `TREE_DIFF_ADDITIONS_ARE_PLANTED`'s stray test (`:271`) inspects *added paths*
  only — **there is no modified-path leg to confirm**, which is the question the tracker's pre-flight asked;
  the answer is no, and it is a limit of the six-canary control, not something to route around by renaming
  files. **(2)** Therefore **planted canaries must be new files whose paths match `CANARY|SENTINEL|canary`**
  (the `:271` vocabulary) — a canary planted by *editing* an existing ordinary path would be invisible to
  every tree assertion, and could only ever be evidenced by the primitive sections, which is a weaker claim
  than "the harness caught it". Canaries #4–#6 keep their ordinary **directories** (`src/…`, `include/…`)
  with the required token in the **filename**; what they cannot keep is a purely in-place edit. **(3)** The
  `DISP UNIVERSE_SHA_MATCHES_PIN` line a non-`real` run prints (`:246`) says "hash compared to run-real, not
  to the pin" — **nothing compares it**; the line is a display, by the file's own rule that `DISP` is not a
  `SENT`. So on a canary run the only thing that pins the input tree is the path-set diff. Noted here rather
  than fixed in the script because fixing it means editing the generator, which mints a `GENERATOR_SHA256`
  and orphans the paste in [`t3-sentinels-real.txt`](t3-sentinels-real.txt): the fix belongs in the same
  commit as the per-tag floor line, and if a content-leg assertion is added it must be **measured on that
  tag**, not seeded from 28 (above).
- **C7's locale arm** (above): unfireable here, and an export drop can pass.
- **`FIND ENTITY_GRANULAR_ROWS_WITHOUT_LINE_EVIDENCE` has no chk.** The literal `1` that S14/S15/S18
  write into column 6 (headed `hits_in_file`) is disclosed, not asserted: comparing it against a
  constant is the tautology this harness has been deleting all cycle, not one it should mint.
- **`FIND SENTINEL_TOTAL_FLOOR_NOT_MEASURED` has no chk either** — see the next bullet, which is worse.
- **The canary tag floors nothing.** The floor is `[ "$TAG" = real ]`-gated; on every other tag the
  script prints a `FIND` line, which is a display and not a failure. `SENTINEL_TOTAL` reads **28** on
  `negctl` against **34** on `real`. That gap is **the tag, not the program**, and the warrant for it is
  **the generator's own source, not any transcript**: walking `t3-census.sh` and matching each `chk` to its
  enclosing tag conditional puts **15 of the 16** names under a guard. The 11 real-only ones sit inside five
  `if [ "$TAG" = real ]; then` blocks — guard lines `:238` (2 names), `:251` (2), `:1156` (1), `:1435` (4),
  `:1561` (1) — and the 5 non-`real`-only ones inside two `if [ "$TAG" != real ]; then` blocks, `:259` (the

## 5 · Three-leg freeze check, after every run on this page

The census reads the tree and writes only under `/tmp/opencode/basalt-audit/t3/`; the mutated copies
were created inside `context/audit/scripts/` as `.neg-<name>.sh` **and deleted** (`git status
--porcelain` over the repo after each batch: no residue). So the audited tree was never written to —
which is the claim the plan's single-leg `git diff` version of this check could not actually support:

    $ cd vendor/basalt
    $ GIT_NO_LAZY_FETCH=1 git diff --quiet dc047a77beeddf1e91234d983a91d6bf929e9619 && echo "AUDIT TREE OK (tracked contents)" || echo "AUDIT TREE DRIFTED — STOP"
    AUDIT TREE OK (tracked contents)
    $ N=$(find . -type f -not -path './.git/*' | wc -l); [ "$N" -eq 862 ] && echo "TREE FILE COUNT OK (862)" || echo "TREE FILE COUNT=$N — untracked additions — STOP"
    TREE FILE COUNT OK (862)
    $ U=$(git status --porcelain --ignored | grep -c .); [ "$U" -eq 0 ] && echo "TREE CLEAN (no untracked/ignored)" || { echo "TREE NOT CLEAN: $U entries — STOP"; git status --porcelain --ignored | head; }
    TREE CLEAN (no untracked/ignored)

Why three legs and not one: `server/basalt/.gitignore` line 1 is `/vendor/`, so `git diff <pin>`
compares tracked contents and cannot see an ignored untracked file. That is the whole of
[`t3-tree-contamination.txt`](t3-tree-contamination.txt).
