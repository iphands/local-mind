## 1 · Method, and why it is not `gh`

The plan's Verify block says `gh api …`. **`gh` is not installed in this session**
(`command -v gh` → nothing); the tracker's environment list claiming it works is wrong and is
corrected in the plan. Everything upstream below came from `curl` over TLS to
`https://api.github.com` (API v3), **unauthenticated**.
Per Rule E the comparison is against GitHub's response, never against our own clone's self-claim.

```bash
PIN=dc047a77beeddf1e91234d983a91d6bf929e9619
curl -sS https://api.github.com/repos/jesdga95/basalt                     # repo metadata
curl -sS "$API/commits/$PIN"                                              # commit + verification
curl -sS "$API/commits?per_page=1"                                        # is the pin basalt's tip?
curl -sS "$API/tags?per_page=100"                                         # basalt's OWN tags (95 ≠ Strata's)
curl -sS "$API/git/trees/3f7b69ae…?recursive=1"  -o tree.json             # THE witness
```

Two limits on this method, both learned the hard way in this session:

- The unauthenticated quota is **60 requests/hour** and this task consumed it. No further API probing
  is available from an agent session once exhausted; `git ls-remote` and `git fetch` are **not**
  rate-limited, which is what made the git-protocol tests in [`t2-lineage.txt`](t2-lineage.txt) possible.
- **Querying a *peer* repository's commit endpoint for our SHAs is not a valid presence test.** GitHub
  resolves a commit against a repo's object store, not against its default branch, and this upstream
  has rewritten its mainline — so a `200`/`422` split proved nothing about shared history. That method
  is retired; the sound one is a pristine `--filter=tree:0` clone plus the promisor **full-40-hex**
  probe. See [`t2-lineage.txt`](t2-lineage.txt) § 0 (R1) and § 1, and `../../pitfalls.md`.

## 6 · Blame-boundary diagnostic (does the 72 % figure rest on blame's stopping points?)

`--line-porcelain` marks a commit it will not walk past with a `boundary` header line. Lines credited
to a boundary or to the repository's root commit are credited to whoever last *moved* them, not
whoever wrote them. Measured over the **80** first-party censused files — the denominator defined in
§ 5 (`87` census rows − `6` `BINARY_SKIPPED` − `1` vendored `stb_image.h`); that list, not any of the
`86` / `87` variants, is what every figure on this page divides by:

```text
lines=20111   boundary_lines=560 (2.78%)   root_commit_lines=560 (2.78%)
files_with_boundary_lines=7 of 80
```

```text

  51  include/basalt/platform/direct_file.hpp
  17  include/basalt/platform/memory.hpp
 184  serve/chat_template.jinja
  72  src/platform/direct_file.cpp
  14  src/platform/memory.cpp
 178  tools/tokenizer.py
```

  CORRECTED 2026-11-05 — **this section first published `boundary_lines=0 (0.00 %)` and the sentence
  "no blame line in the census sits on a boundary". Both were false.** The figure came from a grep of
  the blame output for the string `boundary` with no anchor. Blame porcelain *echoes the source line*,
  so that pattern also matches identifiers and comments (`/// … a prefetch window starts on a page
  boundary.` in `memory.cpp`, and `boundary` in `CMakeLists.txt`); anchored to the header form
  `^boundary( <40-hex>)?$` the true count is **560 lines in 7 files**. A fourth green-but-wrong result
  in this task's own tooling. The exact command, since the naive one is the trap:
  `git blame --line-porcelain $PIN -- "$f" | grep -cE '^boundary( [0-9a-f]{40})?$'`.

**The 560 boundary lines are exactly the 560 root-commit lines** — not merely equal totals: per-file
counts match for all 80 files, so it is one population, not two that coincide. `|A|=560 |B|=560`,
per-file mismatches 0. The cause is the root commit itself: blame cannot walk past a commit with no
parent, so every line still credited to `f2a08d4b` is *by definition* a boundary line.

So the honest reading is **the opposite of what this section first claimed: 2.78 % of the audited
lines do rest on blame's stopping point**, and no share below is free of it. But the 2.78 % is not an
*error bar* — it is a **lineage** quantity, not an uncertainty. Those 560 lines are inherited from
before the fork (they are the ancestor project's initial bulk import: `f2a08d4b`, 2026-09-24,
**Niko1221**, "Strata: Qwen3.8-Flash-Next on a 12-24 GB NVIDIA GPU + 64 GB RAM, one-click install",
219 files / 50,165 insertions). Their author is unknown to blame and knowable another way: they sit in
the 1,001-line `inherited` bucket below, where the credited author is Niko1221 for 94.8 % of them.
Attributing them to "whoever imported them" is the correct label, and it is why the § 5 shares are
published twice. Files where the root dominates: `serve/chat_template.jinja` 184/184,
`tools/tokenizer.py` 178/303, `include/basalt/platform/direct_file.hpp` 51/67.

## 8 · Side effect the census had on the "frozen" clone

Blame on a `blob:none` partial clone **lazy-fetches blobs**, so T2 wrote to the object store. T1
ran its checks under `GIT_NO_LAZY_FETCH=1`; this census deliberately did not, and could not.

```text
git count-objects -v  →  in-pack 19352 · packs 752 · size-pack 53992 KiB · loose 0 · garbage 0
```

The tree hash still matches (§3) and the worktree is still porcelain-clean, so the pin did not
move; but the clone is no longer blob-empty, and the census is only re-runnable offline *because*
it has now run once.

Two limits that bound what this can be used for, both load-bearing:

1. **A trailer is disclosure, not authorship.** It records what the committer claimed about how the
   commit was made. The defensible sentence is *"the audited history self-identifies as substantially
   AI co-authored"*, never "AI-authored the code". `86.9 %` is a share of commits, `97.9 %` a share of
   blamed lines (both the corrected values above); neither is a share of *code originality*.
2. **The upstream `8 of 5637` is not evidence that upstream is human-written.** That line of history
   was rewritten, and the only measured delta of the rewrite is the removal of exactly this trailer
   family ([`t2-lineage.txt`](t2-lineage.txt) § 5: on 844 byte-identical commit pairs, Claude trailers
   1,049 ours vs 0 theirs, human co-authors 22 vs 22, Codex 3 vs 3). Post-edit, upstream's trailer
   corpus is not a disclosure record at all. AI involvement is **established in our line** and
   **unresolved in theirs, where the disclosure was removed**.

Consequences for Plan 02, recorded here in advance so the triager is not surprised into either panic
or complacency later:

- **Base rates change.** A substantially AI-generated codebase produces *inadvertent* sinks —
  hallucinated URLs, copied examples carrying a debug endpoint, dead config plumbing — and dead code
  at volume. Two predictions, stated before T3/T8 run: **the orphan-config-key section (currently
  billed as the highest-signal malice residue) will return a large volume of benign AI residue**, and
