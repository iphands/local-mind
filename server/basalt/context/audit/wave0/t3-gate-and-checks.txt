narrowed). `PRODUCT_B=3 AUDIT_B=5` **matches the owner line** — `RULES.md` § *Expected counts*, bumped

## 4 · Scope evidence (condition (3))

Producer is `RULES.md`'s own pre-commit twin, run against the **staged** set. Two passes, because this
file stages after the first reading — every number below is a printed line, and the pair is what makes
the self-exclusion checkable rather than asserted:

```text
PASS 1  (12 paths staged, this file not among them)
FILES=11 SCOPE_HITS=0
PATTERNS=^(run|build|Dockerfile|Dockerfile\.dockerignore|versions\.env|lib/|models|\.gitignore)

PASS 2  (this file staged as well)
FILES=12 SCOPE_HITS=0
PATTERNS=^(run|build|Dockerfile|Dockerfile\.dockerignore|versions\.env|lib/|models|\.gitignore)
```

`PATTERNS` is pasted as run output, not copied from the definition: if the list is amended later, this
line says which list these hits were computed against.

Two scope limits on those lines, both measured rather than assumed:

- **They count this project's files only.** The producer strips `^server/basalt/`, so a commit touching
  the monorepo root is under-counted by design — 11 of 12 in pass 1, 12 of 13 in pass 2. This commit
  does touch it: `context/pitfalls.md` (the locale host-limit copy) is invisible to the strip. So the
  whole-commit variant was run too, and `SCOPE_HITS=0` is **not** an artifact of the narrower input:

  ```text
  PASS 1  FILES_ALL=12 SCOPE_HITS_ALL=0
  PASS 2  FILES_ALL=13 SCOPE_HITS_ALL=0
  ```

  with the strip-excluded path tested against `PAT` on its own returning `hits=0`. The machine
  condition behind the carve-out therefore holds over every path in the commit; only the *file count*
  is project-scoped.
- **Neither pass can measure the commit object**, and pass 1 cannot see the file carrying it.
  `t2-gate-and-checks.txt` § 8 is the precedent for recording the staged passes and letting the next
  commit carry the landed one. A third run, after § 4 itself was widened to carry these numbers, printed
  `FILES=12 SCOPE_HITS=0` again — measured, not inferred, though inference would have been safe here:
  editing a staged file changes no path and removes none.

## 5 · The freeze pairing — committed script vs the run that cites it

`t3-sentinels-real.txt` is worthless as evidence if the `t3-census.sh` next to it is a different
program. Verified on the **index**, which is what git writes into the commit tree:

```text
staged t3-census.sh = 1bab1ec5e7933c90a80a97aa875218351052280445d585bfce6645f036128106
staged t3-inputs.sh  = 327bf7c3f4460a0a3fdb60a3e1782ac25317babb3b80426aefe91929b4251d5e
paste                = GENERATOR_SHA256=1bab1ec5e7933c90a80a97aa875218351052280445d585bfce6645f036128106
```

Equal for `t3-census.sh`. Re-check in one line from the commit object (any later session):

```bash
git cat-file blob <sha>:server/basalt/context/audit/scripts/t3-census.sh | sha256sum
# must equal the GENERATOR_SHA256= line of t3-sentinels-real.txt
```

`t3-inputs.sh` has no token in the paste — it is the *producer* of the three `INPUT_SHA256=` legs, so
its pairing is indirect: re-running `scripts/t3-inputs.sh && scripts/t3-census.sh vendor/basalt real`
must reproduce those three hash lines. Its own hash is recorded here so a later edit is attributable.

Note the shape of that pairing: **it is a pairing, not a proof.** If the two scripts and the paste all
change together they stay mutually consistent while describing neither the tree nor any run anyone
watched. What anchors them to the world is the third leg — the tree — in § 6.
