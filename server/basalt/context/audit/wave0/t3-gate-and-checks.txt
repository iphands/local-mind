when the premise is wrong"), and `RULES.md` is a file this plan edits. So the ranges are pinned to the
blob they were cut from:

```bash

# ba991abfee7220ebf13f9df1dfe5a465f962ac64b158d2ce807e966174772b29   ← the block § 2 pastes output of
```

`3d296696…` **is** `context/plans/RULES.md` as committed in `dd94598`
(`git rev-parse dd94598:server/basalt/context/plans/RULES.md`). Both commands above were run and printed

## 5 · The freeze pairing — committed script vs the run that cites it

`t3-sentinels-real.txt` is worthless as evidence if the `t3-census.sh` next to it is a different
program. Verified on the **index**, which is what git writes into the commit tree:

```text
staged t3-census.sh = 1bab1ec5e7933c90a80a97aa875218351052280445d585bfce6645f036128106
staged t3-inputs.sh  = 327bf7c3f4460a0a3fdb60a3e1782ac25317babb3b80426aefe91929b4251d5e
paste                = GENERATOR_SHA256=1bab1ec5e7933c90a80a97aa875218351052280445d585bfce6645f036128106
```

Equal for `t3-census.sh`. Re-check in one line from the commit object (any later session):

```bash
git cat-file blob dd94598ae6562fa723c70666b225269a3f29cc2b:server/basalt/context/audit/scripts/t3-census.sh | sha256sum
# must equal 1bab1ec5e7933c90a80a97aa875218351052280445d585bfce6645f036128106
#          == the GENERATOR_SHA256= line of t3-sentinels-real.txt
```

`t3-inputs.sh` has no token in the paste — it is the *producer* of the three `INPUT_SHA256=` legs, so
its pairing is indirect: re-running `scripts/t3-inputs.sh && scripts/t3-census.sh vendor/basalt real`
must reproduce those three hash lines. Its own hash is recorded above so a later edit is attributable,
and **one has happened**: `a207f9a` added the input-set totals asserts (`INPUT_TSVS=12`,
`INPUT_ROWS=862`, exit 4) to `t3-inputs.sh`, moving its sha
`327bf7c3f4460a0a3fdb60a3e1782ac25317babb3b80426aefe91929b4251d5e` →
`812edf09da0ac20b69e4ae0da51c0f2b3c02c0d4d8be5feab0a417479edabc65`. The pairing survives because the
edit is a **guard, not a projection**: the script was re-run and all three produced files are
byte-identical (`diff -r` of a pre-edit snapshot is empty) and still equal, in order, to the
`INPUT_SHA256=` legs pasted in `t3-sentinels-real.txt`. `t3-census.sh` itself is untouched
(`1bab1ec5…`). Both new asserts were fired before staging — dropping a TSV gives
`INPUT_TSVS=11 … exit 4`, dropping one row gives `INPUT_ROWS=861 … exit 4` — and neither control could
overwrite the real inputs, because the guards sit **before** the script's writes.

Note the shape of that pairing: **it is a pairing, not a proof.** If the two scripts and the paste all
change together they stay mutually consistent while describing neither the tree nor any run anyone
watched. What anchors them to the world is the third leg — the tree — in § 6.

```text

TREE CLEAN (no untracked/ignored)
```

Three legs, all three required — the reason is [`t3-tree-contamination.txt`](t3-tree-contamination.txt),
and the tracker's Resume step 1 now carries all three for the same reason.

**The `INTERPRETER=` line.** Step 1 gained it in this commit because a prerequisite stated as an exact
version in prose fails silently closed when the shell moves; the echo is part of the gate's own record
every time. That is the whole claim this file makes about it — the history of the `python3 (3.14.10)`
line it replaces, including why that number was not itself wrong, is in
`context/pitfalls.md` § *A dated fact scoped to a shell I could not enter…* and the tracker's Notes, not
here.

Two honest limits on it, stated next to the output rather than defended:

- **Nothing machine-checks its presence.** `RULES.md` § *Project gate* requires the line to be pasted,
  and no `FAIL` fires if a paste drops it — unlike 1b's identity guard or 2b's enumerated file list. This
  is a deliberate exception: the line is evidence about the *environment*, it gates nothing, and a guard
  that fails a commit for a missing informational line invites the failure mode this plan documents
  (a green step read as a covered one). If it is ever used as a threshold, it needs a guard first.
- **All three legs now print `MISSING` on failure.** The first cut guarded only `python=`, so a shell
  with no `command -v python3` would have printed `at=` — indistinguishable from a formatting quirk.
  Fixed in the follow-up commit; § 1's paste above predates that edit and shows a fully-populated line.
