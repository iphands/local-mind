## 1 · What actually works (the sound method)

1. **Pristine partial clone** of the peer: `--filter=tree:0`, no checkout. Commits only, seconds, 2.6 MB.
2. **Promisor full-OID probe.** Ask the pristine partial clone for a **full 40-hex** SHA. A miss
   triggers a real fetch from the peer's `upload-pack`; the server's answer is object-level and
   quota-free: `fatal: remote error: upload-pack: not our ref <sha>` = **not reachable from any ref
   this remote advertises**. Abbreviated SHAs cannot be requested this way (promisor needs full OIDs)
   and produce a *local* `Not a valid object name` that looks identical to a negative — R1 again.
3. **Content key** `(tree, author-date, committer-date, subject)`, and for files the blob SHA.
   **Commit-SHA *identity* does not track the same work across these two repositories** (§ 3–5): the same
   work exists under different hashes, which is why items 3 and 4 — not SHA equality — are the join keys.
   (Not "SHA comparison is meaningless": blob SHA and patch-id comparisons between the two repos are exactly
   what T2b/U12 must do. The qualifier is the load-bearing part of this sentence.)
4. **Patch-id** (`git patch-id --stable`) as a third, ancestry-free join key — registered for T2b,
   not yet run.
   Superseded framing, do not reuse: "1,236 of 2,194 commits are after 2026-10-06, therefore
   basalt-only". Basalt-side-ness is now *no content-key match*, never *a date*.

## 11b · Both histories in **one** object store — the direct measurement (added same day, 2026-11-05)

Every measurement in §§ 1–5 compared two *separate* clones, so "0 shared SHAs" was an inference across a
boundary. This closes it. A fresh scratch store fetched **both** projects from GitHub with the same
command, so there is no cross-repo boundary left to distrust and no query history of ours to contaminate it:

```bash

# (typed with a `|| git -C $T fetch --filter=tree:0 basalt '+refs/tags/*:refs/tags/basalt/*'` fallback; the
#  first branch returned 0 so the fallback never ran. `--tags` and `--no-tags` do NOT conflict — the explicit
#  refspec is what decides, `--no-tags` only suppresses the automatic follow. Verified by re-running fetch 3
#  alone after `update-ref -d` on all three refs: the tags and the composition listing below came back
#  identical, in-pack 7834, refs 5. Note the side effect of that re-verification: `--tags` *also* writes bare

# NOTE the trap I hit here: FETCH_HEAD is overwritten by the *next* fetch. Capturing it into a named
# ref immediately after each fetch is mandatory; doing both update-refs at the end names two refs at
# one commit, and the first run had to be thrown away and re-run for exactly that reason (it "found"
# merge-base = ffa80d73 between a ref and itself). Caught only because for-each-ref printed one SHA twice.
```

Store hygiene (`refs/remotes/basalt/main` = `dc047a77…`, `refs/remotes/strata/main` = `ffa80d73…`, plus the
three `refs/tags/basalt/*`): `promisor=true`, `partialclonefilter=tree:0`, **no
`objects/info/alternates`**, 5 refs — **and note that "5 refs" is the state after the `update-ref -d` cleanup
described in the fetch-3 note above, not the state during measurement**; `in-pack 7834` was the same before
and after that cleanup, so the counts below were unaffected by it. Composition, not just the total — which is
the only thing that could show an unexpected object hiding in a sum that otherwise looks right:

```text
git cat-file --batch-all-objects --batch-check='%(objecttype)' | sort | uniq -c

         3 tag           ← basalt's three annotated tags, from fetch 3
    (zero tree and blob objects: the tree:0 filter held)
count-objects -v:  count 0 (no loose objects)   in-pack 7834   packs 3
```

**Three fetches are consistent with every object in the store** — two histories plus three tag objects, no
unexplained object class, nothing loose, no alternates. (The histogram proves the *type split and totals*, not
per-object provenance; what it rules out is an object of a kind, or from a source, the procedure does not
permit.) Every count below was re-run under `GIT_NO_LAZY_FETCH=1` and returned identical numbers with
`rc=0` and empty stderr; that guard protects the *future*, so the composition listing above is what
protects the *past* — without it, a lazy-fetched object would have been silently absorbed into a total that
looked correct.

```text
commits from each ref, set arithmetic:  |A|=2194  |B|=5637  |A∩B|=0  ONLY_IN_A=2194  ONLY_IN_B=5637

git merge-base  basalt/main strata/main        → rc=1, NO OUTPUT (silent — see the correction below)
git merge-base --all …                         → rc=1, 0 lines
git merge-base --is-ancestor pin→strata        → rc=1 (false)
git merge-base --is-ancestor strata→pin        → rc=1 (false)
git merge-base --independent …                 → 2 tips   ← NOT a test of relatedness, see the refutation
git rev-list --count basalt/main..strata/main  → 5637  = |strata|   exactly
git rev-list --count strata/main..basalt/main  → 2194  = |basalt|   exactly

POSITIVE CONTROL (same store, a pair that IS related) — basalt's own v0.2.1 vs the pin:
  merge-base        → 1b3f69641c98…  rc=0        is-ancestor → rc=0
  rev-list --count v0.2.1..pin → 3
  (merge-base between a ref and itself → rc=0, prints the ref: the empty output above is not a git quirk)

REFUTATION OF MY OWN CONTROL (same session): basalt main vs origin/multimodel —
  merge-base → 1b3f6964… rc=0  (related!)      merge-base --independent → 2 tips, identically
  ⇒ --independent answers "does either input reach the other?", which any divergence answers with 2.
```

**What this fixes about the published record.**

1. **`git merge-base` does not print "no merge base."** It exits **1 and prints nothing**, the dangerous
   form, because `mb=$(git merge-base A B)` yields an empty string in a script that never checked `$?`.
   The unrelated-histories test is the **`|A∩B| = 0`** above — a set intersection of two `rev-list` outputs,
   whose marginal counts are printed alongside it (`|A|`, `|B|`), because an empty intersection is also what
   a *failed* `rev-list` produces. The marginals are what make the zero mean something.
2. **`--independent` is not an unrelatedness probe** and I had published it as one in three files. It is
   git's input-reduction step ("neither input reaches the other"), which is true of *any* divergence — the
   `main`/`multimodel` pair above returns 2 with a merge-base, from the same command in the same minute.
   It confirms neither tip contains the other; pair it with the `rc` of plain `merge-base`, never use it
   alone.
3. **The `A..B == |B|` rows are a cross-check, not a second measurement.** Given `|A∩B| = 0` measured
   directly, `A..B = |B|` is arithmetic (B minus nothing); the value of printing it is that a *different
   implementation* of the same set difference — `rev-list`'s ancestry walker rather than my `comm` — agrees
   in both directions against independently counted totals.
4. **Three mechanisms, two sources, for the engine fact.** `v0.2.1..pin = 3` here by local `rev-list`; by
   GitHub's `compare/v0.2.1...main` (Plan 01); and by local blob identity over the engine paths
   (`t2-provenance.txt` § 6). The first two both rest on *what `jesdga95/basalt` publishes today*, so if the
   tag moved they would agree wrongly; the genuinely independent corroboration is § 11's
   `multimodel..main = 3` with merge-base = the `v0.2.1` peel target, measured in a **different clone from a
   different ref pair**. Stated as three mechanisms and two sources, not three independent confirmations.
